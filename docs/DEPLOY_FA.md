# راهنمای استقرار Chat2DB (نسخه فارسی، تحت وب)

این سند نحوه اجرای Chat2DB Community را به‌صورت یک سرویس تحت وب با Docker توضیح می‌دهد.
رابط کاربری این نسخه فارسی است و زبان پیش‌فرض روی فارسی تنظیم شده است.

---

## پیش‌نیازها

فقط دو چیز روی سرور لازم است:

- **Docker** نسخه ۲۰.۱۰ یا بالاتر
- **Docker Compose v2** (دستور `docker compose`)

نیازی به نصب Java، Node.js، Maven یا Yarn روی سرور نیست — همه‌چیز داخل خود Docker ساخته می‌شود.

منابع پیشنهادی سرور:

| منبع | حداقل | پیشنهادی |
|---|---|---|
| CPU | ۲ هسته | ۴ هسته |
| RAM | ۲ گیگابایت | ۴ گیگابایت |
| فضای دیسک | ۵ گیگابایت | ۱۰ گیگابایت |

> نکته: مرحله‌ی **ساخت** ایمیج سنگین‌تر از اجرای آن است (کامپایل فرانت‌اند و بک‌اند).
> اگر سرور شما کم‌منابع است، ایمیج را روی یک ماشین قوی‌تر بسازید و طبق بخش
> [انتقال ایمیج به سرورهای دیگر](#انتقال-ایمیج-به-سرورهای-دیگر) منتقل کنید.

---

## راه‌اندازی سریع

```bash
git clone https://github.com/techwikicto-cyber/Chat2DB.git
cd Chat2DB
docker compose -f docker/docker-compose.yml up -d --build
```

اولین ساخت بسته به سرعت شبکه و سرور حدود **۱۰ تا ۲۵ دقیقه** طول می‌کشد.
پس از آن، برنامه روی این نشانی در دسترس است:

```
http://127.0.0.1:10825
```

بررسی وضعیت:

```bash
docker compose -f docker/docker-compose.yml ps
docker compose -f docker/docker-compose.yml logs -f
```

## اگر ساخت به‌دلیل مخزن npm شکست خورد

این پروژه به‌صورت پیش‌فرض از مخزن `registry.npmmirror.com` (آینه‌ی چینی npm) استفاده می‌کند.
اگر شبکه‌ی شما به این آدرس دسترسی ندارد، ساخت در مرحله‌ی `yarn install` متوقف می‌شود.

راه‌حل — یک مخزن دیگر را جایگزین کنید. ساده‌ترین راه، ساخت فایل `.env` کنار
`docker-compose.yml` است:

```env
CHAT2DB_NPM_REGISTRY=https://mirror-npm.runflare.com/
```

مقادیر شناخته‌شده:

| مخزن | آدرس |
|---|---|
| رسمی npm | `https://registry.npmjs.org/` |
| آینه‌ی ایران (Runflare) | `https://mirror-npm.runflare.com/` |
| آینه‌ی چین (پیش‌فرض) | `https://registry.npmmirror.com/` |

یا مستقیماً هنگام ساخت:

```bash
docker build \
  --build-arg NPM_REGISTRY=https://mirror-npm.runflare.com/ \
  -f docker/Dockerfile \
  -t chat2db-fa:latest \
  .
```

نبودِ اسلش پایانی مشکلی ایجاد نمی‌کند و به‌طور خودکار اضافه می‌شود.
این کار هیچ فایلی را در مخزن تغییر نمی‌دهد و فقط روی همان ساخت اثر می‌گذارد.

## ⚠️ امنیت — این بخش را حتماً بخوانید

این نسخه صفحه‌ی ورود دارد و پیش‌فرض روشن است: در اولین اجرا حساب `admin` ساخته
می‌شود و گذرواژه‌اش در لاگ کانتینر چاپ می‌شود. هر حساب هم فضای کاری جدای خودش را
دارد — بخش «صفحه‌ی ورود» پایین‌تر.

با این حال **پیکربندی پیش‌فرض فقط روی `127.0.0.1` گوش می‌دهد**، و این عمدی است:

- **رمزگذاری در کار نیست.** سرویس روی HTTP ساده کار می‌کند، پس اگر مستقیم روی
  اینترنت باز شود گذرواژه‌ی ورود و همه‌ی نتایج کوئری در مسیر قابل شنود است.
- **اگر `CHAT2DB_DISABLE_LOGIN=true` بگذارید هیچ دروازه‌ای نمی‌ماند** و هر کسی که
  به پورت برسد به همه‌ی اتصال‌های ذخیره‌شده دسترسی کامل دارد.
- **حساب کاربری، دسترسی دیتابیس نیست.** هر اتصال گذرواژه‌ی همان دیتابیس را با
  خودش دارد؛ صاحب اتصال هر کاری که آن گذرواژه اجازه می‌دهد می‌تواند بکند.

### اگر می‌خواهید از راه دور به آن دسترسی داشته باشید

**هرگز** فقط `CHAT2DB_BIND_ADDRESS=0.0.0.0` را تنظیم نکنید و آن را روی اینترنت باز نگذارید.
یکی از این سه روش را انتخاب کنید:

**۱. تونل SSH (ساده‌ترین و امن‌ترین برای استفاده‌ی شخصی)**

سرویس روی سرور همچنان فقط روی `127.0.0.1` می‌ماند و شما از سیستم خودتان تونل می‌زنید:

```bash
ssh -L 10825:127.0.0.1:10825 user@your-server
```

سپس در مرورگرِ سیستم خودتان `http://127.0.0.1:10825` را باز کنید.

**۲. پروکسی معکوس با TLS و احراز هویت**

> ⚠️ اگر از پروکسی معکوس استفاده می‌کنید، حتماً بخش
> [مبدأهای مجاز](#مبدأهای-مجاز-cors) را بخوانید، وگرنه فونت‌ها بارگذاری نمی‌شوند.

سرویس را پشت Nginx / Caddy / Traefik قرار دهید که هم HTTPS را مدیریت کند و هم
کاربر را احراز هویت کند (مثلاً Basic Auth، OAuth2 Proxy یا Authelia).
نمونه‌ی Nginx با Basic Auth:

```nginx
server {
    listen 443 ssl;
    server_name db.example.com;

    ssl_certificate     /etc/letsencrypt/live/db.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/db.example.com/privkey.pem;

    location / {
        auth_basic           "Chat2DB";
        auth_basic_user_file /etc/nginx/.htpasswd;

        proxy_pass http://127.0.0.1:10825;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # پاسخ‌های جریانی هوش مصنوعی نباید بافر شوند
        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

ساخت فایل رمز عبور:

```bash
sudo htpasswd -c /etc/nginx/.htpasswd myuser
```

**۳. شبکه‌ی خصوصی / VPN**

سرویس را فقط روی یک رابط شبکه‌ی داخلی یا VPN (مثلاً WireGuard یا Tailscale) منتشر کنید:

```bash
CHAT2DB_BIND_ADDRESS=10.8.0.1 docker compose -f docker/docker-compose.yml up -d
```

## مبدأهای مجاز (CORS)

سرور در نسخه Community فقط به درخواست‌هایی پاسخ می‌دهد که مبدأ (`Origin`) آن‌ها را
بشناسد. مبدأیی که خودِ سرویس روی آن سرو می‌شود همیشه مجاز است، پس در حالت عادی
(دسترسی مستقیم به `http://IP:10825`) نیازی به تنظیم ندارید.

اما اگر پشت **پروکسی معکوس** هستید، مرورگر مبدأ عمومی را می‌فرستد
(مثلاً `https://db.example.com`) در حالی که درخواست با نام داخلی به سرور می‌رسد.
در این حالت باید مبدأ عمومی را صریحاً اعلام کنید:

```env
CHAT2DB_COMMUNITY_ALLOWED_ORIGINS=https://db.example.com
```

چند مبدأ را با کاما جدا کنید.

> **نشانه‌ی فراموش‌کردن این تنظیم:** صفحه بالا می‌آید و حتی وضعیت ورود را می‌خواند،
> ولی دکمه‌ی ورود کار نمی‌کند و در کنسول مرورگر `POST /api/community/auth/login`
> خطای **۴۰۳** می‌گیرد. دلیلش این است که مرورگر برای `GET` هم‌مبدأ هدر `Origin` را
> نمی‌فرستد ولی برای `POST` می‌فرستد — پس همه‌چیز سالم به‌نظر می‌رسد تا اولین باری
> که می‌خواهید کاری انجام دهید.
>
> از نسخه‌های اخیر، سرور دلیل رد شدن را در لاگ می‌نویسد:
>
> ```bash
> docker compose -f docker/docker-compose.yml logs | grep "Refused"
> ```
>
> در آن خط هم مبدأیی که مرورگر فرستاده و هم مبدأیی که سرور تصور می‌کند خودش است
> نوشته شده، پس معلوم می‌شود کدام را باید در `CHAT2DB_COMMUNITY_ALLOWED_ORIGINS`
> بگذارید. راه دیگر: در nginx هدر `Host` اصلی را رد کنید
> (`proxy_set_header Host $host;`).

## کلید رمزنگاری

Chat2DB رمز عبور اتصال‌های پایگاه‌داده و کلیدهای API مدل‌های هوش مصنوعی را با
**AES-256-GCM** رمزنگاری می‌کند و برای این کار به یک کلید نیاز دارد.

در این نسخه، اگر کلیدی تعیین نکنید، هنگام اولین اجرا به‌طور خودکار یک کلید امن
ساخته و در این مسیر داخل والیوم داده ذخیره می‌شود:

```
/root/.chat2db-community/config/encryption.key
```

> ⚠️ **هشدار مهم:** اگر این کلید را از دست بدهید، هیچ‌کدام از رمزهای عبور و
> کلیدهای API ذخیره‌شده دیگر قابل رمزگشایی نیستند. حتماً از والیوم داده
> پشتیبان بگیرید (بخش [پشتیبان‌گیری](#پشتیبانگیری-و-بازیابی)).

### تعیین کلید به‌صورت دستی

اگر می‌خواهید کلید را خودتان مدیریت کنید (مثلاً برای اجرای چند نمونه با داده‌ی مشترک):

```bash
# ساخت یک کلید ۳۲ بایتی با کدگذاری Base64
openssl rand -base64 32
```

سپس آن را در فایل `.env` کنار `docker-compose.yml` قرار دهید:

```env
CHAT2DB_COMMUNITY_ENCRYPTION_KEY=<کلیدی که ساختید>
```

## تنظیمات قابل شخصی‌سازی

این متغیرها را می‌توانید در فایل `.env` یا هنگام اجرای دستور تنظیم کنید:

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `CHAT2DB_PORT` | `10825` | پورتی که روی سرور منتشر می‌شود |
| `CHAT2DB_BIND_ADDRESS` | `127.0.0.1` | آدرسی که سرویس روی آن گوش می‌دهد |
| `CHAT2DB_JAVA_OPTS` | `-Xmx2g` | تنظیمات JVM (مثلاً سقف حافظه) |
| `CHAT2DB_COMMUNITY_ENCRYPTION_KEY` | (خودکار) | کلید رمزنگاری |
| `CHAT2DB_IMAGE_TAG` | `latest` | برچسب ایمیج |
| `CHAT2DB_APP_VERSION` | `5.3.0` | نسخه‌ی نمایش‌داده‌شده در برنامه |
| `CHAT2DB_EAGER_INIT` | `false` | با `true` همه‌ی اجزای برنامه هنگام راه‌اندازی ساخته می‌شوند نه در اولین درخواست؛ اولین باز شدن صفحه کمی سریع‌تر می‌شود، ولی اگر جزئی از کار بیفتد کل کانتینر بالا نمی‌آید. اولین اجرا را با `docker compose logs -f` ببینید |
| `CHAT2DB_COMMUNITY_PASSWORD` | (خالی) | گذرواژه‌ی مشترک صفحه‌ی ورود. اگر خالی باشد هیچ ورودی در کار نیست و هر کسی که به پورت برسد دسترسی کامل دارد |
| `CHAT2DB_AI_SQL_TIMEOUT_SECONDS` | `300` | سقف زمان اجرای کوئری‌هایی که **هوش مصنوعی** می‌نویسد. کوئری‌های خود شما در کنسول محدود نمی‌شوند. روی جدول‌های خیلی بزرگ این تنها چیزی است که جلوی یک اسکن کامل ناخواسته را می‌گیرد؛ `0` یعنی بدون محدودیت |
| `CHAT2DB_COMMUNITY_ALLOWED_ORIGINS` | (خالی) | دامنه‌های اضافی مورد اعتماد مرورگر، جدا شده با کاما. فقط وقتی لازم است که یک reverse proxy آدرس واقعی را پنهان کند |

## صفحه‌ی ورود

صفحه‌ی ورود **به‌صورت پیش‌فرض فعال است** و هیچ تنظیمی لازم ندارد. کانتینر در اولین اجرا یک گذرواژه می‌سازد، آن را در لاگ چاپ می‌کند و در والیوم داده نگه می‌دارد:

```bash
docker compose -f docker/docker-compose.yml up -d
docker compose -f docker/docker-compose.yml logs | grep -A4 "Sign-in password"
```

خروجی چیزی شبیه این است:

```
[chat2db]  Sign-in password (generated on first start):
[chat2db]
[chat2db]      a89w_T5eUS2wHcp3QEdTGRWW
```

تمام درخواست‌های `/api` بدون نشست معتبر با خطای ۴۰۱ رد می‌شوند — یعنی محافظت واقعی است، نه فقط پنهان کردن صفحه.

**برای گذاشتن گذرواژه‌ی دلخواه خودتان** `CHAT2DB_COMMUNITY_PASSWORD` را در `docker/.env` تنظیم کنید (فایل باید کنار `docker-compose.yml` باشد، نه در ریشه‌ی مخزن؛ اگر ترجیح می‌دهید ریشه بماند با `--env-file .env` صریح معرفی‌اش کنید). با `docker compose -f docker/docker-compose.yml config` می‌توانید ببینید مقدار واقعاً منتقل شده یا نه.

**برای حذف کامل صفحه‌ی ورود** `CHAT2DB_DISABLE_LOGIN=true` بگذارید. فقط وقتی منطقی است که سرویس روی `127.0.0.1` باشد.

### کاربران و مدیریت آن‌ها

اولین اجرا یک حساب **`admin`** می‌سازد که گذرواژه‌اش همان چیزی است که در لاگ چاپ شده. با آن وارد شوید، بعد از **تنظیمات ← حساب کاربری** برای بقیه حساب بسازید.

اگر بنر گذرواژه را در لاگ پیدا نکردید — مثلاً چون والیوم داده از قبل وجود داشته و فایل دوباره ساخته نشده — مستقیم از خود فایل بخوانیدش:

```bash
docker exec chat2db-community cat /root/.chat2db-community/config/password
```

### گذرواژه‌ی admin را گم کرده‌اید؟

`CHAT2DB_COMMUNITY_PASSWORD` را در `docker/.env` بگذارید و کانتینر را ری‌استارت کنید. این متغیر **در هر بار راه‌اندازی** اعمال می‌شود، نه فقط اولین بار: حساب `admin` با آن گذرواژه بازنشانی، فعال و به نقش مدیر برگردانده می‌شود.

```bash
echo 'CHAT2DB_COMMUNITY_PASSWORD=گذرواژه‌ی-جدید' >> docker/.env
docker compose -f docker/docker-compose.yml up -d
```

بعد از اینکه وارد شدید، این خط را از `.env` بردارید — وگرنه هر ری‌استارت دوباره گذرواژه را به همان مقدار برمی‌گرداند و تغییری که از داخل برنامه داده‌اید از بین می‌رود. سرور هم موقع اعمال، این هشدار را در لاگ می‌نویسد.

ادمین می‌تواند کاربر اضافه کند، نقش هر کس را بین «مدیر» و «کاربر» عوض کند، کسی را غیرفعال کند یا حذف کند. هر کسی هم می‌تواند گذرواژه‌ی خودش را از همان صفحه عوض کند.

- غیرفعال کردن یا حذف یک حساب، نشست‌های باز آن را **بلافاصله** می‌بندد؛ لازم نیست منتظر انقضا بمانید.
- آخرین مدیرِ فعال نه حذف می‌شود، نه غیرفعال، نه تنزل می‌یابد — وگرنه هیچ‌کس دیگر نمی‌تواند وارد پنل مدیریت شود.
- گذرواژه‌ها با PBKDF2-HMAC-SHA256 و نمک جداگانه ذخیره می‌شوند، در `~/.chat2db-community/storage/user/user.json` داخل والیوم داده. خودِ گذرواژه هیچ‌جا نوشته نمی‌شود.
- نام کاربری بین ۲ تا ۳۲ نویسه از حروف انگلیسی، رقم، نقطه، خط تیره و زیرخط. گذرواژه دست‌کم ۸ نویسه.

نکته‌های مهم:

- **هر حساب فضای کاری مستقل خودش را دارد.** اتصال‌ها، کنسول‌ها، تاریخچه، داشبوردها و نمودارها فقط برای همان کسی دیده می‌شوند که ساخته‌شان؛ مدیر هم استثنا نیست و چیزی بیشتر از بقیه نمی‌بیند. هر فضای کاری در `~/.chat2db-community/<profile>/storage/users/<نام-حساب>-<هش>/` جدا نگهداری می‌شود، پس جداسازی ساختاری است نه فیلترِ زمان خواندن.
- **جداسازی داده جای دسترسی دیتابیس را نمی‌گیرد.** هر اتصال، گذرواژه‌ی همان دیتابیس را با خودش دارد و صاحبش هر کاری که آن گذرواژه اجازه می‌دهد می‌تواند بکند. نقش «کاربر» فقط جلوی مدیریت حساب‌ها را می‌گیرد. برای محدود کردن کسی روی یک جدول، در خود دیتابیس یوزری با دسترسی مناسب بسازید.
- **اولین بالا آمدن بعد از این تغییر، داده‌ی قبلی را به مدیر می‌دهد.** هر چه تا امروز مشترک بود به فضای کاری تنها مدیرِ فعال منتقل می‌شود و بقیه‌ی حساب‌ها از صفر شروع می‌کنند. چیزی حذف نمی‌شود؛ فقط جابه‌جا می‌شود، و در لاگ کانتینر نوشته می‌شود چه چیزی کجا رفت.
- **تنظیمات هر حساب روی سرور ذخیره می‌شود.** پوسته، زبان، فونت، تنظیمات ویرایشگر و جدول، و مدل انتخاب‌شده‌ی هوش مصنوعی به حساب کاربری می‌چسبند نه به مرورگر؛ پس با همان یوزر روی مرورگر یا دستگاه دیگر همان چیزها را می‌بینید. در `storage/user/preferences.json` نگهداری می‌شوند. تب‌ها و چیدمان پنجره عمداً محلی مانده‌اند — آن‌ها وضعیت همان نشست‌اند نه ترجیح کاربر.
- **حذف یک حساب، فضای کاری‌اش را حذف نمی‌کند.** پوشه‌اش سر جایش می‌ماند. اگر حسابی با همان نام دوباره ساخته شود، همان فضای کاری را تحویل می‌گیرد.
- **مدل‌های هوش مصنوعی هم مال هر حساب جداست.** پیکربندی مدل‌ها (شامل کلید API) روی سرور و به تفکیک حساب در `ai-model-configs.json` ذخیره می‌شود، پس روی هر مرورگر و هر دستگاهی با همان حساب همان مدل‌ها را می‌بینید و هیچ حسابی مدل‌های دیگری را نمی‌بیند. اگر قبلاً مدلی تعریف کرده بودید، در اولین ورود بعد از این نسخه به‌طور خودکار از مرورگر به سرور منتقل می‌شود.
- **درایورهای JDBC سفارشی هم مشترک‌اند** (`storage/custom-driver.json`)؛ مثل خودِ درایور، متعلق به نصب هستند نه به یک نفر.
- **اگر MCP را روشن کرده‌اید** (پیش‌فرض خاموش است)، بدانید که MCP با توکن دسکتاپ کار می‌کند نه با حساب کاربری، و به همین دلیل فضای کاری مشترک را می‌بیند — که بعد از انتقالِ بالا خالی است.
- نشست‌ها فقط در حافظه‌ی سرور نگهداری می‌شوند؛ با ری‌استارت کانتینر همه از سیستم خارج می‌شوند. مدت اعتبار هر نشست ۷ روز است.
- کوکی نشست `HttpOnly` و `SameSite=Lax` است و فقط روی HTTPS پرچم `Secure` می‌گیرد.
- اگر سرویس روی اینترنت عمومی است، این را جایگزین TLS و reverse proxy ندانید؛ گذرواژه روی HTTP ساده در مسیر قابل شنود است.

نمونه‌ی فایل `.env`:

```env
CHAT2DB_PORT=8080
CHAT2DB_BIND_ADDRESS=127.0.0.1
CHAT2DB_JAVA_OPTS=-Xmx4g
```

## انتقال ایمیج به سرورهای دیگر

نیازی نیست روی هر سرور ایمیج را از نو بسازید. یک بار بسازید و منتقل کنید.

**روش ۱ — از طریق فایل (بدون نیاز به رجیستری):**

```bash
# روی ماشین سازنده
docker save chat2db-fa:latest | gzip > chat2db-fa.tar.gz
scp chat2db-fa.tar.gz user@target-server:/tmp/

# روی سرور مقصد
gunzip -c /tmp/chat2db-fa.tar.gz | docker load
```

**روش ۲ — از طریق رجیستری خصوصی:**

```bash
docker tag chat2db-fa:latest registry.example.com/chat2db-fa:5.3.0
docker push registry.example.com/chat2db-fa:5.3.0

# روی سرور مقصد
docker pull registry.example.com/chat2db-fa:5.3.0
```

سپس روی سرور مقصد، در `docker-compose.yml` بخش `build` را حذف یا کامنت کنید تا
از ایمیج آماده استفاده شود.

## پشتیبان‌گیری و بازیابی

همه‌ی داده‌ها (اتصال‌ها، تاریخچه‌ی کوئری‌ها، کلید رمزنگاری) در والیوم
`chat2db-community-data` قرار دارند.

**پشتیبان‌گیری:**

```bash
docker run --rm \
  -v chat2db-community-data:/data:ro \
  -v "$(pwd)":/backup \
  alpine tar czf /backup/chat2db-backup-$(date +%F).tar.gz -C /data .
```

**بازیابی:**

```bash
docker compose -f docker/docker-compose.yml down

docker run --rm \
  -v chat2db-community-data:/data \
  -v "$(pwd)":/backup \
  alpine sh -c "rm -rf /data/* && tar xzf /backup/chat2db-backup-YYYY-MM-DD.tar.gz -C /data"

docker compose -f docker/docker-compose.yml up -d
```

## عیب‌یابی

**کانتینر بالا نمی‌آید یا مدام ری‌استارت می‌شود**

```bash
docker compose -f docker/docker-compose.yml logs --tail=100
```

**خطای مربوط به کلید رمزنگاری**

اگر پیام خطایی درباره‌ی `encryption key` دیدید، یعنی متغیر
`CHAT2DB_COMMUNITY_ENCRYPTION_KEY_FILE` به فایلی اشاره می‌کند که وجود ندارد.
یا فایل را در آن مسیر mount کنید، یا متغیر را خالی بگذارید تا کلید به‌طور خودکار ساخته شود.

**ساخت در مرحله‌ی `yarn install` گیر می‌کند**

بخش [اگر ساخت به‌دلیل مخزن npm شکست خورد](#اگر-ساخت-بهدلیل-مخزن-npm-شکست-خورد) را ببینید.

**اتصال به پایگاه‌داده‌ای روی خود سرور میزبان برقرار نمی‌شود**

از داخل کانتینر، `localhost` به خود کانتینر اشاره می‌کند نه به سرور.
به‌جای آن از `host.docker.internal` استفاده کنید و این بخش را به سرویس اضافه کنید:

```yaml
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

**کمبود حافظه هنگام ساخت**

مقدار حافظه‌ی در دسترس Docker را افزایش دهید، یا ایمیج را روی ماشین دیگری بسازید و
طبق بخش انتقال ایمیج منتقل کنید.
